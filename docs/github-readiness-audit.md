## 첫 설치본 배포 전 처리

### 5. Windows CI

`.github/workflows/`가 없습니다. Windows 환경에서 다음을 확인하는 CI가 필요합니다.

1. `cargo fmt --all -- --check`
2. `cargo clippy --locked --all-targets -- -D warnings`
3. `cargo test --locked`
4. Tauri CLI를 명시적으로 설치한 후 NSIS 번들 빌드

현재 통합 테스트는 `examples/fake_cswap.exe`를 사용합니다. 특정 통합 테스트만 실행하는 명령은 예제 빌드를 별도로 요구할 수 있으므로, 깨끗한 체크아웃에서 전체 테스트 경로를 검증해야 합니다. 테스트용 exe가 설치본에 포함되지 않는지도 확인해야 합니다. Tauri는 GitHub Actions 배포 구성을 공식 안내합니다. [공식 파이프라인 문서](https://v2.tauri.app/distribute/pipelines/github/)

### 6. 테스트의 실제 시작프로그램 변경

`src/autostart.rs:112` 이하 테스트는 실행 사용자의 실제 HKCU Run 키에 `ClaudeSwapBar` 값을 쓰고 지웁니다. 복구 가드와 프로세스 내부 Mutex는 있지만, 강제 종료 시 복구되지 않을 수 있고 다른 테스트 프로세스나 실행 앱과의 동시 변경은 막지 못합니다. 복구 오류도 `Drop`에서 무시합니다.

레지스트리 접근 대상으로 테스트 전용 키를 주입하는 방식이 우선입니다. 실제 Run 키 검증은 별도의 명시적 통합 테스트로 분리하고 임시 Windows 사용자나 VM에서 수행하는 편이 좋습니다. 현재 상태의 전체 테스트를 일반 개발자의 설정에 부작용 없는 테스트로 소개하면 안 됩니다.

### 10. 메뉴를 열어도 새 사용량이 메뉴에 즉시 반영되지 않음

`src/main.rs:410`의 메뉴 열기 경로는 `MenuUpdate::Skip`으로 데이터와 툴팁만 갱신합니다. 이후 메뉴를 다시 여는 것만으로 새 메뉴가 만들어지지도 않습니다. 다음 타이머·수동 갱신·전환 후 재구축까지 메뉴의 수치는 예전 값일 수 있습니다.

README의 “메뉴를 열 때 갱신” 설명에 이 차이가 없습니다. 표시된 메뉴를 안전하게 갱신하는 구조를 마련하거나, 현재 동작을 알려진 제약으로 명시해야 합니다.

### 11. 타이머·전환 완료 시 열린 메뉴 교체 위험

`src/main.rs:267`, `:304`는 메뉴를 교체합니다. 타이머 실행 또는 계정 전환 도중 사용자가 메뉴를 다시 열면 재구축과 겹칠 수 있습니다. 코드 주석과 설계 5절도 팝업이 닫히거나 클릭이 유실될 수 있는 잔여 위험으로 기록합니다.

메뉴를 오래 열어 둔 상태, 전환 직후 재열기, 갱신 요청 중첩을 검증해야 합니다. 현재 보고서는 가능한 모든 해결책이 없다는 기존 문서의 주장까지 확인한 것은 아닙니다.

### 12. 계정 전환 요청의 중복 실행

`src/main.rs:499`는 요청마다 스레드와 `cswap switch`를 시작합니다. `busy`는 list 갱신만 묶고 switch는 직렬화하지 않습니다. 사용자가 다시 메뉴를 열어 연속 선택하면 여러 전환 요청이 겹칠 수 있습니다.

실제 자격증명 손상은 확인되지 않았으며 상위 CLI의 잠금 동작에 따라 달라집니다. 다만 마지막 선택의 의미를 명확히 하려면 전환 진행 상태를 표시하고, 진행 중 추가 요청을 막거나 순서대로 처리해야 합니다.

### 13. 실행 파일 탐색과 복구

- `src/cswap.rs:77`은 PATH 탐색 성공 시 절대경로가 아닌 `cswap` 문자열을 저장합니다. 실행 대상을 한 번 확정하고 전체 경로를 보관하는 방식이 진단과 실행 일관성에 유리합니다.
- `src/main.rs:314`의 refresh는 저장된 경로가 있는 동안 재탐색하지 않습니다. 실행 파일 삭제 후 다른 경로에 재설치하면 이전 경로를 계속 사용하여 재시작이 필요할 수 있습니다.
- 시작 시 `find_exe()`가 트레이 생성 전에 실행되므로 `--version` 응답이 멈추면 약 10초 동안 아이콘이 나타나지 않을 수 있습니다.
- PATH 변경은 이미 실행 중인 프로세스에 자동 반영되지 않습니다. 설치 후 재시작 안내가 필요합니다.

### 14. 툴팁 길이와 Unicode

`src/menu.rs:229`는 길이를 Rust `chars()` 기준으로 제한합니다. 같은 파일의 Windows 제한 설명은 UTF-16 코드 단위 기준입니다. 이모지처럼 두 UTF-16 단위를 쓰는 문자가 포함되면 현재 길이 검사와 실제 제한이 달라집니다. UTF-16 길이를 기준으로 자르고 해당 입력을 테스트해야 합니다. 실제 Windows 화면의 잘림 형태는 이번에 확인하지 않았습니다.

### 15. 오류 진단과 표시

- 시작 실패는 `expect`로 종료하고 메뉴 생성·적용 오류는 일부 무시합니다. 릴리스 GUI 프로세스에서는 콘솔도 없으므로 사용자에게 원인이 보이지 않을 수 있습니다.
- 최소 진단 정보는 앱 버전, cswap 버전, 실행 경로, 오류 종류, 종료 코드 정도가 적절합니다. stdout 전체나 계정 JSON을 그대로 로그에 남기는 방식은 피해야 합니다.
- 한국어가 아닌 `usageStatus`와 CLI stderr도 그대로 표시합니다. README의 “동작 이름 외 모든 상태·오류는 한국어”라는 문장은 정확하지 않습니다.
- cp949 stderr 테스트는 문자가 사라지지 않는지만 검증하며, 올바른 한국어 표시를 검증하지 않습니다. 현재 구현은 UTF-8 손실 변환을 사용합니다.

### 16. cswap 버전 호환성

최소 또는 실제 검증한 cswap 버전이 기록되어 있지 않습니다. fixture 기반 테스트는 실제 설치된 CLI와의 호환성을 보증하지 않습니다. 릴리스마다 실제 버전의 JSON 응답과 전환 명령을 확인해야 합니다.

상위 프로젝트는 현재 `lastGoodUsage` 같은 추가 필드도 문서화합니다. 이 앱은 해당 필드를 무시하므로 일부 오류 상태에서 상위 CLI가 보존한 마지막 사용량을 표시하지 못합니다. 이는 필수 호환성 오류로 단정할 수 없으며 표시 기능 개선 후보입니다. “cswap이 발전해도 계속 정확하다”는 README 표현은 검증 범위에 맞게 줄이는 편이 좋습니다. [상위 JSON 계약](https://github.com/realiti4/claude-swap#json-output-for-scripting)

## 유지보수 문서와 저장소 정리

### 17. 기여·문제 신고 문서

다음 파일을 작은 규모로 추가하는 것이 적절합니다.

- `CONTRIBUTING.md`: Windows 개발 준비, 검사 명령, 테스트 부작용, PR 기준
- `SECURITY.md`: 보안 문제 신고 경로와 토큰·계정 파일을 공개 이슈에 첨부하지 않는 안내
- `.github/ISSUE_TEMPLATE/bug_report.yml`: Windows 버전, 앱/cswap 버전, 설치 방식, 재현 절차
- `.github/pull_request_template.md`: 문제, 변경 결과, 검증
- `CHANGELOG.md`: 최초 공개 버전과 알려진 제약

앱이 직접 자격증명을 저장하지 않고 cswap에 위임한다는 점, 앱이 남기는 설정은 시작프로그램 Run 값이라는 점도 README에서 설명하면 좋습니다. 공개 연락처와 보안 신고 채널은 소유자가 정해야 합니다.

### 18. ignore와 줄바꿈 정책

루트 `.gitignore`는 `/target/`, `/gen/`만 포함합니다. `.superpowers/sdd`는 내부 `.gitignore` 때문에 현재 정상 제외되어 있습니다. 이미 무시되는 작업 기록이 바로 업로드된다고 판단해서는 안 됩니다.

앞으로 생길 `.env`, 인증서·개인키, 계정 내보내기 파일, 로컬 로그·임시파일에 대한 좁은 패턴을 검토해야 합니다. 필요한 테스트 파일과 아이콘을 숨기는 광범위한 패턴은 피해야 합니다. `.gitattributes`와 선택적인 `.editorconfig`는 Windows/Linux 기여 환경의 줄바꿈 차이를 줄이는 데 도움이 됩니다.

### 19. 설계·계획 문서의 현재성

설계 문서는 상태가 여전히 “구현 계획 대기”이며 실제 구현과 다른 내용이 있습니다. 예를 들어 비활성 계정의 회색 표시, 환경 버전, 포터블 배포 범위가 현재 코드·README와 일치하지 않습니다. 계획 문서에는 과거 구현과 미완료 체크박스가 대량으로 남아 있습니다.

개인정보를 제거한 뒤 과거 기록임을 명시하고, 현재 구조·제약은 별도 짧은 문서에 유지하는 방법이 적절합니다. 기존 문서 전체를 삭제할 필요는 없습니다.

### 20. 의존성 점검

의존성 취약점 점검이나 업데이트 자동화 설정이 없습니다. 릴리스 전에 잠금 파일 기준의 알려진 취약점·라이선스 검토를 수행하고, 이후 Cargo 의존성 업데이트 알림을 마련하는 것이 좋습니다. 이번에는 취약점 데이터베이스 검사나 라이선스 전수 검토를 수행하지 않았습니다. 취약한 의존성이 발견되었다는 뜻은 아닙니다.
